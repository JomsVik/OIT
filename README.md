# ОИТ — рабочий портал на Rust

Сервер исходной ветки `2-version` переписан с Node.js на Rust (Axum). Интерфейс сохраняет дизайн оригинала: светлый компактный экран входа IT Портал, тёмную админку с синей палитрой, верхнее меню, карточки заявок и оформление таблиц. Улучшены отступы, читаемость, фокус полей и адаптация под небольшие экраны. Сохранены разделы заявок и их архива, задач и обсуждений, отчётов, инвентаря, коммутаторов с портами, пользователей и сотрудников ОИТ. Добавлен склад картриджей в том же стиле. JavaScript используется только в браузере; Node.js для запуска не нужен.

База данных — SQLite, схема создаётся и обновляется автоматически из `migrations/`. Сервер и интерфейс собираются в один исполняемый файл. Для отдельной виртуальной машины основной способ установки — **Ubuntu без Docker, через systemd**.

**[Пошаговая установка на Ubuntu без Docker](deploy/UBUNTU.md)** — подключение через PuTTY, сборка, настройка, автозапуск, обновление и резервная копия. В этом варианте база находится в `/var/lib/oit/oit.sqlite3`.

Docker оставлен как дополнительный вариант ниже. Для него база хранится в `data/` рядом с проектом.

## Быстрый запуск на Ubuntu

Потребуются установленный Docker Engine и плагин Compose: [официальная установка для Ubuntu](https://docs.docker.com/engine/install/ubuntu/). Скопируйте всю папку проекта на сервер, например в `/opt/oit-source`.

```bash
cd /opt/oit-source
bash deploy/prepare.sh
sudo docker compose up -d --build
curl --fail http://127.0.0.1:3000/api/health
sudo docker compose logs --tail=100 portal
```

Скрипт спросит пароль первого директора и подготовит каталоги с владельцем UID 10001. Логин — `director`, пароль — введённый вами. Минимум 12 символов. Стандартного пароля нет. Если ввели неподходящий пароль, заполните `BOOTSTRAP_PASSWORD` в `.env` вручную перед запуском. Создаваемый директор используется только при пустой таблице администраторов: изменение `.env` позже не меняет существующий пароль.

По умолчанию порт доступен только на самом сервере. Выберите один способ доступа:

* Через Nginx: скопируйте `deploy/nginx.conf` в `/etc/nginx/sites-available/oit`, замените имя сервера, включите конфигурацию и выполните `sudo nginx -t`, затем `sudo systemctl reload nginx`. Для HTTPS добавьте сертификат организации и установите `COOKIE_SECURE=true` в `.env`, затем `sudo docker compose up -d --force-recreate`. Nginx передаёт исходный Host, который используется для защиты запросов.
* Напрямую внутри рабочей сети: задайте в `.env` `LISTEN_IP=IP_ВАШЕГО_СЕРВЕРА` и `PORT=3000`, выполните `sudo docker compose up -d --force-recreate`. Открывайте `http://IP_СЕРВЕРА:3000`. Для HTTP оставьте `COOKIE_SECURE=false`. Доступность порта определяется настройками сети и межсетевого экрана организации.

## Как работать с картриджами

1. Войдите сотрудником ОИТ, откройте **Картриджи**. Создайте карточку модели: название, первый штрихкод, совместимость, порог пополнения. Штрихкод хранится текстом, начальные нули сохраняются.
2. Выберите **Приход партии**, введите количество, при необходимости номер накладной. Поставьте курсор в поле штрихкода и отсканируйте. Enter сохраняет приход.
3. Если у новой партии другой штрихкод, раскройте **Новый штрихкод у существующей модели**, выберите модель и привяжите код. Все коды одной карточки изменяют общий остаток. Привязка кода сама по себе не создаёт приход.
4. Для установки выберите **Выдача**, укажите кабинет / получателя; можно выбрать принтер из инвентаря. Сканируйте: одна операция списывает ровно **1 штуку**. Место установки сохраняется для следующих сканирований. При смене места измените его перед сканированием.
5. **Возврат на склад** увеличивает остаток с записью причины в примечании. Ошибочный приход сейчас исправляется учётной операцией, история не удаляется; отдельного акта инвентаризации в этой версии нет.

Сканер должен работать в режиме HID / USB-клавиатуры, с суффиксом Enter. Ручной ввод также работает. COM-сканеры потребуют настройки HID либо отдельного адаптера. Реальный сканер здесь не подключался: Enter-сценарий проверен через браузер. Учитывается количество по модели, а не жизненный цикл каждого физического экземпляра.

Остаток не уходит ниже нуля. Изменение остатка и запись журнала выполняются в одной транзакции. Повтор запроса с тем же номером операции не проводит её второй раз. Если ответ сервера потерян, используйте **Повторить неподтверждённую операцию**: номер сохраняется в этом браузере, в том числе после обновления страницы. Новое физическое сканирование после успешной выдачи считается новой выдачей.

Журнал показывает последние 500 операций; полная история остаётся в БД. В нём есть модель, количество, остаток после операции, сотрудник, место, выбранный принтер, примечание и время. Несколько штрихкодов привязываются к модели; раздельные остатки по партиям не ведутся.

Имя сотрудника и отсканированный код сохраняются в каждой новой операции: переименование или удаление сотрудника не стирает его имя из истории. Для старых операций, созданных до миграции 004, исходный отсканированный код неизвестен и остаётся пустым.

## Если на рабочем сервере нет интернета

На другой Linux-машине с интернетом, Docker и той же архитектурой процессора выполните `sudo bash deploy/bundle-offline.sh`. Он соберёт образ и подготовит папку `oit-offline/` с образом, конфигурацией и `START.txt`. Перенесите её на рабочий сервер. Там достаточно загрузить образ (`sudo docker load -i oit-portal-image.tar.gz`), запустить `bash deploy/prepare.sh`, настроить `.env` и выполнить `sudo docker compose up -d --no-build --pull never`. Rust и доступ к реестрам пакетов на рабочем сервере не нужны. Docker и Compose должны быть установлены заранее. Готовый Linux-образ в этой поставке отсутствует: скрипт нужно выполнить на Linux с Docker.

## Доступ и существующие разделы

* Пользователь создаёт и видит свои заявки, пишет публичные комментарии. По коду отслеживания после входа можно открыть заявку и её публичные комментарии.
* Администратор работает с заявками, складом, инвентарём, сетью, создаёт задачи и меняет статус назначенных ему задач.
* Главный администратор и директор редактируют задачи и удаляют рабочие записи.
* Директор управляет учётными записями, ролями и паролями. Последнего директора удалить или понизить нельзя. Изменение учётной записи завершает её сессии.

Роли проверяются сервером по сессии, переданный браузером `admin_id` / `admin_role` не даёт прав. Сессия действует 8 часов, хранится в HttpOnly-cookie. Пароли хешируются bcrypt, хеши не отдаются API. После 10 неудачных попыток входа для одной учётной записи действует ограничение до конца 15-минутного окна. Внутренние комментарии доступны только ОИТ. Текст выводится безопасными DOM-методами.

Отчёты формируются из выполненных заявок, выполненных задач, статистики заявок по дням или текущих остатков картриджей. Это сохранённые снимки: дальнейшие изменения источника не меняют старый отчёт. Доступны просмотр таблицы, добавление и изменение строк, выгрузка CSV и редактирование исходного JSON. Изменение строк отчёта не изменяет сами заявки, задачи или складские остатки.

## Резервная копия, перенос и восстановление

Резервное копирование работающей базы использует SQLite Backup API:

```bash
sudo bash deploy/backup.sh
```

Копия появится в `backups/`. Копируйте её на отдельный носитель / сервер. Для регулярного копирования администратор сервера может добавить в cron, например `0 2 * * * cd /opt/oit-source && /bin/bash deploy/backup.sh`. Время cron — часовой пояс сервера. Автоматическое удаление старых копий не настроено.

Для переноса на другой сервер сохраните копию БД, исходники (либо Docker-образ) и настройки `.env`. На целевом сервере сначала выполните `prepare.sh`, остановите сервис и поместите копию в `data/oit.sqlite3` с владельцем `10001:10001`, затем запустите Compose. Это переносит пользователей, заявки, склад и историю целиком. Не копируйте отдельно основной файл работающей WAL-базы: используйте команду backup.

Для восстановления на действующем сервере:

```bash
sudo docker compose stop portal
# Сохраните текущую базу и её WAL/SHM-файлы вместе в отдельный каталог.
sudo mkdir -p recovery-before-restore
sudo find data -maxdepth 1 -type f -name 'oit.sqlite3*' -exec mv -t recovery-before-restore -- {} +
sudo cp backups/ИМЯ_КОПИИ.sqlite3 data/oit.sqlite3
sudo chown 10001:10001 data/oit.sqlite3
sudo chmod 600 data/oit.sqlite3
sudo docker compose up -d
curl --fail http://127.0.0.1:3000/api/health
```

Каждый раз используйте новый каталог для сохранения предыдущей базы. При обновлении кода сначала сделайте backup, затем `sudo docker compose up -d --build`; каталог `data` сохранится. Миграции применяются транзакционно при запуске.

## Запуск без Docker

На Ubuntu установите Rust 1.95+ и инструменты сборки (`build-essential`, `pkg-config`), затем:

```bash
cargo test --locked
cargo build --release --locked
cp .env.example .env
# Заполните BOOTSTRAP_PASSWORD в .env.
chmod 600 .env
./target/release/oit-portal
```

Для systemd создайте системного пользователя `oit`, каталоги `/opt/oit` и `/etc/oit`. Скопируйте бинарник в `/opt/oit/oit-portal`, настройки в `/etc/oit/oit.env` (root:root, режим 600). В настройках задайте `DATABASE_PATH=/var/lib/oit/oit.sqlite3` и `BIND_ADDR=127.0.0.1:3000`. Скопируйте `deploy/oit.service` в `/etc/systemd/system/`, выполните `sudo systemctl daemon-reload` и `sudo systemctl enable --now oit`. Каталог базы создаст systemd. Интерфейс уже встроен в бинарник.

Для копирования нативной базы: запустите бинарник от пользователя с доступом к базе, передав тот же `DATABASE_PATH`, и аргументы `backup /путь/к/новой-копии.sqlite3`. Путь назначения должен быть доступен для записи. Сервер от этого не останавливается.

## Старые данные и границы переноса

Оригинальные файлы ветки сохранены в `legacy/` для сравнения и не обслуживаются Rust-сервером. Исходный `init.sql` пуст; данных старой PostgreSQL в репозитории нет. Эта поставка создаёт новую SQLite-базу. Автоматический импорт существующей рабочей PostgreSQL **не реализован**: для сохранения уже накопленных данных нужен её дамп / фактическая схема и отдельный проверяемый перенос. Не заменяйте действующую систему, если в ней есть нужные данные, до такого переноса.

Идентификаторы и названия API основных разделов сохранены по исходнику; публичный интерфейс и правила авторизации обновлены. Интерфейс браузера остаётся на HTML/CSS/JavaScript, серверная логика — Rust. LDAP/AD и почтовые уведомления не настраивались.

## Проверка

`cargo test --locked` проверяет приход, выдачу, возврат, несколько кодов модели, повторы запросов, запрет отрицательного остатка, конкуренцию двух подключений за последнюю единицу, неизменяемый журнал, восстановление backup, сессии, роли, приватность комментариев и базовые операции исходных разделов. `node --check app.js` и `node --check cartridges.js` проверяют синтаксис интерфейса, Node нужен только для этой проверки.

Сборка и тесты выполнялись на Windows. Docker и запуск под Ubuntu в этой среде не выполнялись: Docker здесь не установлен. Для окончательной приёмки на сервере проверьте health, вход, создание модели, приход 2 шт., выдачу 1 шт., повтор запроса и восстановление копии в отдельном тестовом каталоге.
